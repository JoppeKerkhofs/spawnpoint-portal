# The Window (Tauri and Vue) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A desktop window that lists the servers of every linked panel and joins one with a click, shows the instances and their mods, links panels by code, and shows progress while files arrive.

**Architecture:** `src-tauri` is a thin layer: each Tauri command calls one `portal-core` function and turns its error into a string; core's progress channel is forwarded as a `progress` event. No launcher logic lives in `src-tauri` or in Vue. The Vue side is five views switched by one `ref`, with every call to Rust in one typed file, `src/api.ts`.

**Tech Stack:** Tauri v2, Vue 3 with TypeScript, Vite, Tailwind v4 (`@tailwindcss/vite`), `tauri-plugin-opener`, `tauri-plugin-dialog`.

**Spec:** `docs/superpowers/specs/2026-11-19-spawnpoint-portal-design.md` ("The window", the anti-goals). Builds on plans 1 to 4.

## Global Constraints

All earlier plans', plus:

- The window opens before any network call finishes: nothing in Tauri's `setup` touches the network, and every view renders at once and fills in afterwards.
- No launcher logic outside `portal-core`. A command that needs more than "call core, map the error" means the logic belongs in core, with a test there.
- No token or secret ever crosses into the webview: not a panel token, not a pairing secret, not (in plan 6) a Microsoft token.
- Styling follows the panel's look by copying what is needed from `../spawnpoint/panel/resources/css/app.css` and its components, not by sharing a package.
- What each screen looks like is decided with the owner in Task 1, before any view is built.
- Tauri, its plugins and the Vite setup: follow their current documentation (`npm create tauri-app` output and the v2 guides), not memory.
- No router and no store library: one `ref` for the current view, plain `ref`s per view.

## Review Focus

- Clicking Join twice, or Join while that instance is already starting: the second click is refused with "already starting", not a second sync on the same folder. Pinned in Task 2.
- No network at start: the window still opens, the server list says which panel could not be reached, instances are listed and can be opened. Pinned in Task 6's run check.
- A page address from a pack or a panel that is not `https://` (`file:`, `javascript:`, a program path): never opened. Pinned in Task 2.
- A join that fails halfway: the progress view closes, the error is shown in words, and the button works again. Pinned in Task 4.
- A long list (a pack with 300 mods; many servers): the list scrolls inside the window, the navigation stays in place. Pinned in Task 5's run check.

### Task 2: The Tauri crate, state and guards

**Files:**
- Create: `package.json`, `vite.config.ts`, `tsconfig.json`, `index.html`, `src/main.ts`, `src/App.vue`, `src/style.css`, `src-tauri/*`
- Create: `crates/core/src/settings.rs`
- Modify: root `Cargo.toml`, `.gitignore`

**Interfaces:**
- Produces, in core `settings.rs`: `pub struct Settings { pub player_name: String }` (default `Player`), `pub fn load(paths: &Paths) -> Settings` (missing or unreadable file: the default), `pub fn save(paths: &Paths, settings: &Settings) -> Result<()>` at `settings.json`; `pub fn valid_player_name(name: &str) -> bool`: 3 to 16 of `A-Za-z0-9_`.
- Produces, in `running.rs`:
  - `pub struct AppState { pub client: reqwest::Client, pub paths: Paths, pub busy: Mutex<HashSet<String>>, pub pairing: Mutex<Option<(String, Pairing, bool)>> }` (address, pairing, allow_http).
  - `pub fn claim(busy: &Mutex<HashSet<String>>, key: &str) -> Result<Claim, String>`: `Err("already starting")` when `key` is in the set; the returned `Claim` removes it on drop.
  - `pub fn forward_progress(app: &AppHandle) -> ProgressTx`: spawns a task that emits each `Progress` as the event `progress`.
  - `pub fn safe_url(url: &str) -> Result<&str, String>`: `Ok` only for a URL starting with `https://`. The approval page of a panel being paired may be plain http; it has its own command (`open_pairing_page`, Task 3), which opens an address we built, not one we received.

In `tauri.conf.json`: product name `Spawnpoint Portal`, identifier `eu.spawnpoint.portal`, one window 1100 by 720 (minimum 900 by 600), CSP `default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline'`. Capabilities: the core defaults and the dialog plugin's `open` and `confirm`. The opener plugin is called from Rust only, so the webview gets no opener permission.

### Task 3: The commands

**Files:**
- Create: `src-tauri/src/commands.rs`, `src/api.ts`
- Modify: `src-tauri/src/main.rs`

**Interfaces:**
- Consumes: core's `panel`, `join`, `instance`, `play`, `gamefiles`, `settings`; `claim`, `forward_progress`, `safe_url`.
- Produces: these commands, each `async`, each returning `Result<T, String>` with `Error::to_string()`, and in `src/api.ts` one exported function per command with the same name in camelCase plus the TypeScript types of what they return (written by hand after the Rust structs).

| Command | Arguments | Returns | Does |
| --- | --- | --- | --- |
| `servers` | | `Vec<PanelServers { panel: Panel, servers: Vec<Server>, error: Option<String> }>` | `join::all_servers` |
| `join` | `panel_id`, `slug` | `Vec<Manual>` | claims `<panel_id>/<slug>`; `join::join` with the profile from settings; returns once the game has started; a task waits for the game and emits `game-exited` with the instance id |
| `instances` | | `Vec<Instance>` | `instance::list` |
| `instance_mods` | `id` | `Vec<ModFile>` | `instance::mods` |
| `instance_create` | `name`, `minecraft`, `loader: Option<String>` | `Instance` | `Loader::parse`, `instance::create` with `Source::Manual` |
| `instance_delete` | `id` | | claims the id; `instance::delete` |
| `instance_add_mod` | `id`, `path` | | `instance::add_mod` |
| `instance_remove_mod` | `id`, `name` | | `instance::remove_mod` |
| `instance_launch` | `id` | | claims the id; `play::start_instance`; `game-exited` as above |
| `open_mods_folder` | `id` | | opens `game/mods` of that instance with the opener plugin (the path is built from the id through `instance::load`, never received) |
| `open_page` | `url` | | `safe_url`, then the opener plugin |
| `minecraft_versions` | | `Vec<String>` | release ids of `gamefiles::manifest`, newest first, 1.13 and up |
| `panels` | | `Vec<Panel>` | `panel::list` |
| `panel_pair_start` | `address`, `allow_http` | `PairingView { code, approve_at, expires_at, interval }` | `normalize_address`, `pair_start`; keeps the `Pairing` in `AppState.pairing` |
| `open_pairing_page` | | | opens `<address>/settings/api-tokens` of the kept pairing with the opener plugin; nothing kept: an error |
| `panel_pair_poll` | | `Option<Panel>` | `pair_poll` with the kept pairing; on a token: `panel::add`, clear the kept pairing |
| `panel_remove` | `id` | | `panel::remove` |
| `settings_get` / `settings_set` | / `player_name` | `Settings` / | `settings::load` / `valid_player_name`, `save` |

The claim of `join` and `instance_launch` is held until the game process has started, then dropped; the `game-exited` task holds nothing. Events: `progress` (`{ stage, done, total }`) and `game-exited` (`{ instance, code }`).

### Task 5: The five views

**Files:**
- Create: `src/views/Servers.vue`, `Instances.vue`, `InstanceDetail.vue`, `Panels.vue`, `Account.vue`

**Interfaces:**
- Consumes: `api.ts`, `withProgress`, `ManualFiles`; the screens file.

Behaviour the screens file does not decide:
- Every view renders its frame at once and loads in `onMounted`; while loading it shows the previous data when it has some, else a quiet "Loading".
- Servers: `servers()` on mount and on a Refresh button, no timer. Join calls `withProgress('Joining <name>', () => join(panel.id, slug))`; a non-empty answer shows `ManualFiles`. A server whose `state` is not `running` can still be joined (the sync is useful; the game will say it cannot connect), with its state shown.
- Instances: Play calls `instanceLaunch`. The create form takes its versions from `minecraftVersions()`, loaded when the form opens; the loader is a `<select>` of none, Fabric, NeoForge, Forge.
- One instance: "Add a mod" uses the dialog plugin's `open` filtered to `.jar`; Remove and Delete ask for confirmation with the dialog plugin's `confirm`, naming the file or instance.
- Panels: linking shows the code in large type and the approve address as a button (`openPairingPage`), polls `panelPairPoll()` every `interval` seconds, and stops at a panel, at `expires_at`, or when the view is left. An `http://` address shows a checkbox "This panel has no https; link it anyway", which sets `allow_http`.
- Account: one field for the player name with the rule (3 to 16 letters, digits or `_`) beside it, saved with `settingsSet`.
- Every input has a `<label>`; every icon-only button has an `aria-label`; focus is visible.
