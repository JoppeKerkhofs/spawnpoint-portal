# The Window (Tauri and Vue) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The desktop window exactly as designed: Servers, Instances, One instance, Panels and Account in the standard (light, dark) and blocky looks, with the status bar that shows every join and launch, built on the core additions the design needs.

**Architecture:** Two halves. First the core (`crates/core`, hand-written, no Tauri) gains what the design shows and the core lacks: memory, last play, pack version names, skipped and hand-fetch files kept in `instance.json`, unreadable instances, numbered progress, error kinds, and the carried-over runtime work. Then `src-tauri` is a thin layer, one command per core call plus two guards, and the Vue side is five views switched by one `ref`, with every call to Rust in `src/api.ts` and every decision a view makes in a plain `.ts` module with tests.

**Tech Stack:** Rust (core as plans 1 to 4), Tauri v2 with `tauri-plugin-opener` and `tauri-plugin-dialog`, Vue 3 with TypeScript, Vite, Tailwind v4 (`@tailwindcss/vite`), `vitest` (dev dependency, logic tests only).

**Spec:** `docs/superpowers/specs/2026-11-20-window-screens.md` (the screens; its last section, "Decisions by the owner", overrides anything earlier in it) and the boards in `docs/superpowers/specs/window-design/`; `docs/superpowers/specs/2026-11-19-spawnpoint-portal-design.md` (constraints, anti-goals). Builds on plans 1 to 4. "Spec §N" below means a section of the screens spec.

## Global Constraints

All earlier plans', plus:

- The window opens before any network call finishes: nothing in Tauri's `setup` touches the network; every view renders its frame at once and fills in afterwards.
- No launcher logic outside `portal-core`. A command that needs more than "check, call core, map the error" means the logic belongs in core, with a test there. Core crates stay as listed in the product design; Tauri and its plugins are allowed in `src-tauri` only. Ask the owner before adding any other crate or npm package that does launcher work.
- Every sync rule that protects a player's files stays exactly as it is: no existing test in `sync.rs`, `pack.rs` or `join.rs` changes its expectations. New fields only report what the rules already do.
- New fields in `instance.json` are `#[serde(default)]`, so instances written by plans 3 and 4 still load.
- No token, pairing secret or bearer crosses into the webview: not in a command's return value, an event, or an error message.
- Text from panels and packs is rendered as text. `v-html` is forbidden everywhere.
- Only `https://` pages are opened (`safe_url`), except the pairing page, which Rust builds from the address being paired.
- CSP: no remote scripts, styles or fonts; every font is a file under `src/assets/fonts/`.
- Copy is quoted from the spec; values (sizes, colours) are given in the task or referenced as "spec §N, table X". Never paraphrase either.
- No router and no store library: one `ref` for the current view and the open instance id; shared state in plain exported `ref`s.
- Frontend checks: `npx vue-tsc --noEmit` clean for every frontend task. Logic that decides something (formatting, stage text, filters, poll stop conditions, which state a view is in) lives in `src/logic/*.ts` with `vitest` tests in `src/logic/*.test.ts`, run by `npm test` (`vitest run --passWithNoTests`). No component or snapshot tests.
- Rust tests in `src-tauri` call only the helpers in `src-tauri/src/state.rs`. `portal-core` is built without `cfg(test)` there, so any core call that reaches `secrets` (`panel::add`, `remove`, `token`, `join::*`, `panel::servers`) would touch the real Credential Manager. No test contacts a real panel or the network; core tests may use the loopback servers in `download::testing` as they do now.
- `tauri::generate_context!` embeds `dist/`, so Rust verification in window tasks is `npm run build; cargo test --workspace`.
- Tauri, its plugins and Vite: follow their current documentation, not memory.
- Implementers cannot see the window. Checks that need eyes are collected in Task 19 and done with the owner.
- Commit subjects are plain sentences; no trailers; never a token starting with `@`.

## Review Focus

- Clicking Join twice, or Join on a server whose instance is already syncing: the second is refused ("already starting" from `claim`; core's instance lock behind it), never two syncs on one folder. Pinned in Tasks 3 and 7.
- No network at start: the window opens, Servers names each panel that cannot be reached, Instances lists instances and their unreadable folders, an instance opens. Pinned in Tasks 2 and 14 (logic tests) and Task 19 (run check).
- A page address from a pack or a panel that is not `https://` (`file:`, `javascript:`, a program path): never opened. Pinned in Task 7.
- A join that fails halfway: the status bar shows the failure in words with Close; after Close every Join and Play works again; late progress events do not bring the bar back. Pinned in Task 13.
- A changed memory setting or a game ending while the same instance syncs: neither is lost when the sync saves. Pinned in Task 1.

```rust
// download.rs
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct Progress { pub step: u32, pub steps: u32, pub stage: String, pub done: u64, pub total: u64 }
pub fn numbered(stages: Vec<&'static str>, out: ProgressTx) -> ProgressTx
// sync.rs
pub fn plan_with(game_dir: &Path, managed: &[ManagedFile], wanted: Vec<Wanted>, progress: &ProgressTx) -> Result<SyncPlan>
// plan(..) = plan_with(.., &a sender whose receiver is dropped)
// play.rs
pub const SYNC_STAGES: [&str; 2] = ["check", "mods"];
pub fn launch_stages(loader: Option<LoaderKind>) -> Vec<&'static str>
```

- Stages, as sent: `check` (new: one event per wanted file examined, `done` of `total`), `mods`, `java`, `libraries`, `assets`, `loader libraries`, `loader`, and `starting` (new: one event, `done = total = 0`, sent by `play::start` after the last install and before `extract_natives`). Raw senders set `step: 0, steps: 0`.
- `fetch_all` sends `{ stage, done: 0, total }` before its first download, so a stage with nothing to fetch still shows.
- `launch_stages`: `java`, `libraries`, `assets`, then `loader libraries`, `loader` for NeoForge and Forge. Fabric adds none: its libraries arrive in the second `install` and show under the step reached.
- `forge::install`'s early return (already installed) sends `loader libraries` 0 of 0 and `loader` n of n first, so the numbering reaches the last step.
- `numbered` forwards every event with `steps = stages.len()` and `step` = 1 + the index of the event's stage, searched forward only from the current step; a stage not found ahead (a repeated `libraries`, `starting`) keeps the current step. It never goes back.
- `join::sync` and `join::join` share a private helper that numbers events once the loader is known (after `prepare`): `SYNC_STAGES` alone for `sync`, `SYNC_STAGES` then `launch_stages(kind)` for `join`, which passes the same numbered sender to `play::start_instance`. `start_instance` itself does not number; its callers do (`numbered(launch_stages(..), tx)`).
- `pack::install` calls `plan_with` with its progress.
- The command line prints `\r{step}/{steps} {stage} {done}/{total}` when `steps > 0`, else as today.

## Decisions taken while planning

Each line: the decision, and what it costs if wrong.

1. Hand-fetch files and skipped paths are stored in `instance.json` by the sync; "Check again" only tests which stored files now exist, without re-planning or network. Wrong: a file renamed by the player still shows; the next join corrects it.
2. "Skipped" covers wanted files the sync left alone because something not ours (or ours but changed) is in the way, including edited pack configs; hand-fetched files the player placed are not skipped. Wrong: a note that appears for an edited config, which can be read as noise.
3. Several skipped files show as several notes with the designed sentence, and several hand files keep the singular explanation (the plural is not designed). Wrong: a long column of notes for a pack with many clashes.
4. Progress steps are numbered from a fixed stage list per operation (`SYNC_STAGES` plus `launch_stages(loader)`), searched forward only; Fabric's libraries and the second install of a modded version show under the step already reached. Wrong: "Step 5 of 5: Libraries" after "Game assets", which looks odd but never goes backwards.
5. "Checking files" is a real core stage (`check`), one event per wanted file. "Starting" is a stage event, not a step.
6. Memory is stored as `memory_mb` with choices 4096, 6144, 8192, 10240 and the default 4096; `--memory` on the command line still overrides. Last play is `{ started_at, seconds }` written when the game exits, also from the command line.
7. A sync saves with `save_synced`, keeping memory and last play written meanwhile; other window writes during a sync (remove mod, check again) may be overwritten by it. Wrong: a removed pack mod reappears in the list until the next sync.
8. The per-instance lock lives in `pack::install` (two syncs of one instance); launching while syncing is prevented by the window's one-operation rule only. Wrong: from the command line a launch could start during a sync.
9. Error kinds: `io`, `network`, `unreachable`, `panel`, `data`, `unsupported`, `not_ready`, `secret`, `busy`, `other`; the window words only `unreachable` (board copy) and `network` (adds "Check your internet connection, then try again."), and shows the rest as the core's message made into a sentence. Wrong: some messages read technical ("io error: …"); per-kind wording can be added in `errorText` alone.
10. A new panel is named by its host, as the command line does. Wrong: the list shows hosts instead of the panel's own name.
11. The Appearance card copy ("Appearance", "Theme", "Standard", "Blocky", "Light or dark", "Light", "Dark", "Follow Windows", "Stored on this PC only.") is mine; the design has none. Wrong: wording to change in one file.
12. Owner decision 3's "dark outline" on the blocky focus ring is read as spec §6's rule: `#111111` inside cards and dialogs, white elsewhere. Wrong: a two-tone ring is a change in `style.css` only.
13. Standard input borders use `#8a9097` (light) and `#6b737b` (dark) to pass 3:1, though the owner only decided the blocky corrections. Wrong: inputs look darker than the panel's.
14. Sizes use 1,048,576 bytes per MB with one decimal, and any non-zero file shows at least "0.1 MB". Wrong: sizes differ slightly from a browser's.
15. "Last played" says "today", "yesterday" or "on {d} {Month}"; lengths "{h} h {m} min", "{m} min", "less than a minute". When an instance was never played its page shows the default idle line. Wrong: copy to adjust in `lastPlayedText`.
16. The status bar's trailing text follows the board of the current view, as the owner decided by default; with several games running it shows the newest. Wrong: one line to change in `trailing`.
17. Delete dialog: "1 mod" for one, and the "(including your {k} own)" part left out when k is 0. Wrong: wording only.
18. Texture rule: pack machine, Fabric wood, Forge sand, NeoForge machine, none grass, hand-made without loader stone; server tiles in the error state use the error colours.
19. Claim keys are `join:{panel_id}/{slug}` and the instance id; the core lock is the second line behind them.
20. Ubuntu fonts come from the `@fontsource` packages (Latin `.woff2`, with the Ubuntu Font Licence); the Minecraft font is bundled only if a licence allowing it is found, else Task 10 stops and asks.
21. CSP adds `connect-src ipc: http://ipc.localhost` for Tauri's IPC and drops the old plan's `https:` images (no remote image in the design).
22. The servers summary counts running servers over every panel (the board counted the first panel only), as the spec says.
